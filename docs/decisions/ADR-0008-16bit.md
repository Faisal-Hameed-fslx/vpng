# ADR-0008: 16-bit channels are in the first public release

**Status:** accepted
**Date:** 2026-11-12
**Question (roadmap §18.15):** Support 16-bit channels in v1.0, or later?

## Decision

16-bit Gray, GrayAlpha, RGB, and RGBA are part of the v0.1 implementation and
the v1.0 release. Their samples are **little-endian** in the canonical buffer.

## Rationale

* 16-bit support is cheap once the format abstraction is right: it doubles
  `bytes_per_channel` and nothing else changes.
* Deferring it would bake 8-bit assumptions into codecs (palette, predictors,
  entropy models) and make them harder to retrofit later.
* The CLI already byte-swaps to and from PNG's big-endian 16-bit order, which
  exercises the distinction.

## Consequences

* Every exact-round-trip test runs across all eight v0.1 formats, including the
  four 16-bit ones.
* The canonical digest includes the bits-per-channel byte, so 8- and 16-bit
  images of the same dimensions never collide.
* Endianness is fixed as little-endian; a big-endian canonical order would be a
  different format and would need its own ADR.
